# Local App Workshop: Designing a Concept That Holds Up

## The Workshop's Product: A Concept, Not an App

This lesson is hands-on: you design a **mobile app concept** that addresses a real local or regional need, applying the method you built across the previous lessons. Be precise about what you are producing — it is **not** a finished, coded app. It is a **concept**: a framed need, a target user, a core value proposition, a scope/MVP, and a justification against the design principles. That is a complete, defensible unit of work, and it is exactly what feeds the coming practical assignment (Marked Assignment 7).

## The Workshop Protocol: Five Steps in One Period

A hands-on block does not stay productive on its own — it needs a **protocol**. Follow it in order; it sums to a single 35-minute period:

**Step 1 — Frame the need (fast).** Choose a real pain in the school or community. Phrase it as a "How Might We" with a named user and a constraint. This takes a couple of minutes and settles the direction.

**Step 2 — Diverge (brainstorm).** Generate many concept directions from the need — draw from the categories of Lessons 109–113 (culture, news, services/payments, regional needs, universal). No censoring yet.

**Step 3 — Filter (converge).** Run each candidate through the Lesson 114 checklist: constraint floor, low data, localisation, local rails, trust, scope. Kill the impossible, keep and sharpen the real.

**Step 4 — Scope to an MVP.** Nail down the target user, the single core job, and the one essential screen that proves it. If you can't state that screen, the scope is wrong.

**Step 5 — Justify and share.** Write the concept as: *user → value proposition → MVP → why it passes the checklist.* Then present it and let peers interrogate it against the same checklist. The class becomes the quality filter.

## The Assignment 7 Link: This Is How You Get to the Mark

This lesson is the in-class anchor for **Marked Assignment 7** — it is where that assignment is introduced. Rather than a bolt-on, the workshop *is* the setup: the concept you produce here becomes the starting point of the assignment, which you will take forward into a prototype through the mobile-UX lessons to come.

So do the workshop properly, with that in mind:

- **Choose a need you genuinely care about** — you will be living with this concept through the assignment.
- **Keep it scoped** — a small, buildable MVP that truly serves a named user will carry you further than an impressive-but-impossible one.
- **Defend it** — be ready to show why it passes the checklist, because the same checklist will be used to mark it.

The assignment and the workshop are not separate things. The assignment extends, deepens and prototypes the concept you design here.

## The "One-Essential-Screen" Rule

The single most useful scoping tool in the workshop is the **one-essential-screen rule**: every concept must be explainable as *"the one screen without which this app is pointless, and what the user does on it."* For example: *the storm-alert screen a parish uses to see the warning and what to do.* If you can name that screen, your scope is right; if your concept needs six screens to make sense, it is over-scoped and will not survive the assignment timeframe.

## Peer Feedback: The Class as the Checklist

Sharing is where learning multiplies. With a **pitch-and-grill** structure, each group states its user and value proposition in ~30 seconds; then peers **grill** it against the shared checklist. This is not a matter of taste or opinion — it is a structured filter:

- Does it respect the constraint floor?
- Is it genuinely localised / using local rails?
- Would a user trust it with money, data or time?
- Is it a buildable MVP?
- Is the need real and well-framed, not a "cool idea"?

Peer feedback built on the checklist catches scope, constraint and trust flaws early — before they cost marks. And being grilled teaches you to defend a design, which is a mark-worthy skill in itself.

## Common Misconceptions

### "The workshop is just for fun"
It is the assessed practice core. Its output seeds Marked Assignment 7 and must survive the principle and scope checks.

### "A concept is a finished app idea"
It is a framed need + value proposition + MVP you can justify. Sufficient to continue, not a full design.

### "Peer feedback is just opinions"
Against the shared checklist it is a structured filter, catching scope, constraint and trust flaws early.

### "More ambitious concept = better mark"
A small, scoped, definitely-buildable MVP that truly serves a named user beats an impressive-but-impossible one.

### "The assignment is separate from the workshop"
The assignment extends precisely the concept produced here — so workshop quality sets assignment quality.

## Summary

This workshop makes the theory tangible: you design an app **concept** — a framed need, target user, value proposition, MVP and justification — through a five-step protocol: frame the need, diverge, filter through the checklist, scope to one essential screen, justify and share. It is the in-class anchor for **Marked Assignment 7**, whose introduction is part of this period: the concept you design here is the seed you will prototype through the mobile-UX lessons ahead. The one-essential-screen rule keeps scope honest, and peer grilling turns the class into a structured quality filter. Treat it as real work — the concept that survives the checklist is the one that will carry a mark, and everything that follows builds on it.
