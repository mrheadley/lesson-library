# Concept Maps for Site Planning

## Why Start with Concepts, Not Code?

Before writing a single line of HTML or choosing a colour palette, you need to answer a more fundamental question: *what content does this website need, and how does it relate to everything else?* A concept map is the tool that answers that question.

Think of building a website like constructing a building. An architect doesn't start by picking paint colours — they start with a blueprint that shows which rooms exist, how they connect, and which doors lead where. A concept map is your blueprint for content.

## What Is a Concept Map?

A concept map is a visual diagram that shows relationships between ideas, topics, or content areas. It uses **nodes** (boxes or circles) to represent concepts and **labelled connecting lines** to show how those concepts relate.

Unlike a mind map — which radiates outward from a single central idea like spokes on a wheel — a concept map shows explicit relationships *between* multiple concepts. A mind map is great for brainstorming; a concept map is great for planning structure.

### The Building Blocks

- **Node**: A box or circle representing a single concept, topic, or page. In web design, each node might represent a page, a section, or a content category.
- **Connecting line**: A line drawn between two nodes to show they are related.
- **Relationship label**: A word or phrase written on the connecting line that describes *how* the two nodes relate. Examples: "contains," "leads to," "requires," "is related to."
- **Hierarchy**: The general-to-specific arrangement — broadest concepts at the top, most specific at the bottom.
- **Cross-link**: A connection between nodes in different branches that shows a non-hierarchical relationship. For example, a "Recipes" page and an "Ingredients" page might be in different branches but are closely related.

## How Concept Maps Work for Websites

When planning a website, your concept map typically starts with the **homepage** (or the site's core purpose) as the central node. From there, branches represent major sections. Sub-branches represent individual pages or content pieces.

### Worked Example: A School Website

Imagine you're planning a website for your school. Start with a blank page and write "School Website" in the centre. Then ask: *what are the main things a visitor would want to find?*

From the central node, draw branches to:

- **About Us** — school history, mission, leadership
- **Academics** — departments, course catalogue, exam schedule
- **Student Life** — clubs, events, sports
- **Contact** — phone, email, map, enquiry form

Under **Academics**, add sub-branches: "Departments," "Course Catalogue," "Exam Schedule." Under **Student Life**, add "Clubs," "Events," "Sports."

Now add relationship labels. The line from "School Website" to "Academics" might say "features." The line from "Academics" to "Departments" might say "includes." A cross-link from "Events" to "Academics" might say "connects to" (because some events are academic).

### Worked Example: A Personal Portfolio

If you're building a portfolio site for a creative student:

- Central node: **My Portfolio**
- Branches: **Projects**, **Skills**, **About Me**, **Contact**
- Under **Projects**: individual project pages (one per project)
- Cross-link: "Skills" connects to each "Project" page with "demonstrated in"

### Worked Example: A Food Blog

- Central node: **Recipes**
- Branches: **Breakfast**, **Lunch**, **Dinner**, **Desserts**
- Under each meal type: individual recipe pages
- Cross-link: "Ingredients" (a separate branch for ingredient guides) connects to relevant recipe pages with "used in"

## Why Concept Maps Matter

Concept maps do several things that jumping straight into code or wireframes cannot:

1. **They reveal content you haven't thought of.** When you map relationships, you notice gaps — "Wait, if we have an 'Events' section, we probably need a way for users to filter by date."
2. **They expose redundant content.** If two nodes cover the same topic from slightly different angles, you might merge them rather than building two pages.
3. **They identify orphan content.** A node with no incoming connections is content that no other page links to — visitors might never find it.
4. **They enable collaboration.** A concept map on a whiteboard lets the whole team contribute ideas, argue about structure, and reach agreement before any building begins.

## Common Mistakes to Avoid

### "A concept map is just a flowchart"

Flowcharts show a linear sequence: step 1 → step 2 → step 3. Concept maps show *relationships* — and those relationships are rarely linear. A user might jump from "Recipes" to "About" and back to "Desserts" in any order. Your concept map should reflect that flexibility.

### "You need software to make one"

Paper, sticky notes, and a marker work perfectly for early-stage concept mapping. You can photograph the result and digitise it later if needed. Digital tools like Miro, MURAL, or draw.io are great for collaboration and iteration, but they're not a prerequisite.

### "The concept map becomes the sitemap"

The concept map captures *conceptual relationships*; the sitemap translates those into a *navigable page hierarchy*. A concept map might show that "Events" and "Calendar" are closely related, but the sitemap must decide: do they share a page, or get separate pages? That's a design decision the concept map informs but doesn't make.

## Key Terms

| Term | Definition |
|------|-----------|
| Node | A single concept, topic, or page represented as a box or circle |
| Relationship label | A word or phrase describing how two nodes connect |
| Hierarchy | General-to-specific organisational structure |
| Cross-link | A connection between nodes in different branches |
| Orphan content | Content with no clear parent section or incoming links |

## Summary

A concept map is the first step in translating a content brief into a navigable site structure. By mapping out what content exists and how it relates — before worrying about layout, colour, or code — you build a foundation that prevents expensive rework and ensures nothing important gets lost. Start on paper, map the relationships, label the connections, and only then move to sitemaps and wireframes.
