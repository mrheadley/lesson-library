# Planning a Complete Site Structure

## Bringing It All Together

Over the past four lessons, you've learned the individual tools of site planning: concept maps, navigational charts, sitemaps, and hierarchy maps with taxonomy. This lesson synthesises them into a single, integrated workflow — taking a project brief from "here's what we need" to "here's the complete, documented site structure."

The process moves from **abstract to concrete**:

1. **Concept map** → What content exists and how it relates
2. **Navigational chart** → How users move through that content
3. **Sitemap** → Which pages exist and how they nest
4. **Hierarchy map with taxonomy** → How content is classified and labelled

Each step builds on the previous one, and each produces a deliverable that guides the next.

## The Integrated Planning Workflow

### Step 1: Define the Brief
Before mapping anything, clarify what the site is for. Answer these questions:
- What is the site's purpose?
- Who is the primary audience?
- What are the top 3 tasks users need to accomplish?
- What content already exists, and what needs to be created?

### Step 2: Build the Concept Map
Start with the site's core purpose as the central node. Branch outward to major content areas. Label relationships between nodes. Identify cross-links, orphan content, and redundancies.

### Step 3: Create the Navigational Chart
Trace the paths users will take. For each major task ("find the phone number," "read a recipe," "buy a product"), map the sequence of pages and links. This reveals whether your concept map's relationships translate into logical user journeys.

### Step 4: Build the Sitemap
Translate the concept map into a page hierarchy. Decide:
- Which concepts become pages
- How pages nest within sections
- Which pages get primary navigation (5–7 items max)
- Which pages live in secondary navigation or the footer
- What utility pages are needed (contact, privacy policy, 404)

### Step 5: Assign Page Templates
For each page in the sitemap, decide what type of layout it needs:
- **Article page**: Text-heavy content (blog posts, about pages)
- **Gallery page**: Image-focused content (portfolio, photo collections)
- **Form page**: User input (contact, registration, enquiry)
- **Landing page**: Marketing-focused, designed for a single call to action
- **List/index page**: Categories or listings that link to individual pages

### Step 6: Document the Plan
Write a brief planning document that captures:
- The visual sitemap
- A content inventory (list of all planned pages)
- Page-level notes (what each page contains)
- The navigation model (which nav components appear where)
- Rationale for key structural decisions

That last point — **rationale** — is crucial. When new content is added later, the reasoning behind your structure protects it from ad-hoc additions that break the IA.

## Worked Example: Local Business Website

**Brief**: Build a website for a small web design agency.

**Concept Map**:
- Central node: "Agency Website"
- Branches: Services, Portfolio, About, Blog, Contact
- Cross-links: Each Portfolio project connects to the relevant Service; Blog posts connect to Services they mention

**Sitemap**:
```
Home
├── Services
│   ├── Web Design
│   ├── Graphic Design
│   └── Photography
├── Portfolio
│   ├── Project 1
│   ├── Project 2
│   └── Project 3
├── About
├── Blog
│   ├── Post 1
│   └── Post 2
├── Contact
└── (Footer) Privacy Policy | Terms
```

**Page Templates**:
- Home → Landing page
- Services → Article page (one per service)
- Portfolio → Gallery page (grid of projects)
- Individual Project → Article page with image gallery
- Blog → List/index page
- Individual Post → Article page
- Contact → Form page

**Navigation Model**:
- Global nav: Services | Portfolio | About | Blog | Contact
- Local nav: Under Services, show individual service pages
- Footer: Privacy Policy | Terms

## Worked Example: School Event Website

**Brief**: A website for an annual school science fair.

**Sitemap**:
```
Home
├── About the Fair
├── Schedule
├── Exhibits
│   ├── Category 1
│   └── Category 2
├── Judges
├── Registration (Form)
├── FAQ
├── Contact
└── (Footer) Privacy Policy
```

**Page Templates**:
- Home → Landing page
- Schedule → Table/timeline page
- Exhibits → Gallery page
- Registration → Form page
- FAQ → Accordion/details page

## Why Planning Saves Time

The most common objection to planning is: "This is wasted time — let's just start building." But skipping structure planning leads to:

- **Inconsistent navigation**: Different sections use different nav patterns
- **Orphan pages**: Content exists but nothing links to it
- **Rework**: You build three pages, then realise they should have been one page with tabs
- **Label confusion**: Pages are named after internal departments, not user tasks

Even 30 minutes of planning saves hours of re-building. The structure doesn't have to be perfect — it has to be *good enough to start*, with the expectation that it will be refined.

## Common Misconceptions

### "Planning is wasted time"
Skipping structure planning is like building a house without a blueprint. You might end up with rooms that don't connect, hallways that lead nowhere, and a front door that opens into a wall.

### "The structure must be perfect before building"
Version 1 is a starting point, not a final product. Plan enough to start building with confidence, and expect to refine as you go.

### "One person can plan the structure alone"
Site structure benefits enormously from multiple perspectives. Different team members will see different user needs and content relationships. The concept map stage, in particular, thrives on collaborative brainstorming.

## Key Terms

| Term | Definition |
|------|-----------|
| Content inventory | A catalogue of all existing and planned content |
| Content audit | Evaluation of content for quality, relevance, and whether to keep/update/remove |
| Page template | A reusable layout pattern that determines how content is presented |
| Navigation model | A specification of which navigation components appear on which page types |

## Summary

Planning a complete site structure means moving from abstract relationships (concept maps) through user journeys (navigational charts) to concrete page hierarchies (sitemaps) and classification systems (taxonomy). The process is iterative, collaborative, and produces documented deliverables that guide every subsequent phase of design and development. Even brief planning prevents expensive rework — and the structure doesn't need to be perfect, just good enough to build from with confidence.
